# Постоянное наблюдение и семидневная оценка

План предназначен только для отдельной установки этой версии Uptime Kuma.
Рабочий каталог — `/srv/uptime-kuma-pilot`, имя проекта — `uptime-kuma-pilot`.
В примере используется `https://kuma.example.com` с внутренним портом
`127.0.0.1:3041`. Перед установкой подставьте свой домен в обоих шаблонах nginx.

## Что проверяется

Три учебных HTTP-проверки обращаются к отдельному внутреннему сервису:
успешный ответ, постоянный ожидаемый отказ и минута отказа каждые десять минут.
Все они начинаются с `Pilot/`. Группа «Пробный запуск 7 дней» объединяет их
для проверки отчётов. Внешние уведомления не настроены. Ожидаемый отказ
учебной проверки не означает отказ самой Uptime Kuma.

Таймер без даты окончания каждые пять минут сохраняет состояние приложения,
перезапуски, память, нагрузку и свободное место. Это отдельные наблюдения,
по ним нельзя доказывать непрерывную доступность между запусками таймера.
Пропущенные интервалы остаются пропущенными. В конце первых семи суток создаётся
`trial-result.json`: из 2016 ожидаемых интервалов отдельно указаны успешные,
неуспешные и пропущенные. Дата начала не сбрасывается повторной командой.

Раз в сутки после 03:10 по Москве сохраняется числовая сводка наблюдений,
затем полная копия данных с проверкой восстановления базы. Время выбрано
до штатной очистки подробной истории Uptime Kuma в 03:14. Если таймер не
сработал вовремя и часть истории очищена, сводка честно покажет отсутствие
данных. Итоговый остаток периода сохраняется в `reports/final-checks.json`.
Если получить его не удалось, итог явно требует проверки владельцем.

Подробная история старше суток может очищаться самой Uptime Kuma. Для недели
следует рассматривать сохранённые суточные сводки и копии. Повторный отчёт
в интерфейсе после очистки может иметь меньшую долю наблюдений. Общий предел
отчёта — 50 000 записей; три проверки с шагом 30 секунд за полную неделю
могут его превысить. Выбирайте сутки или отдельные проверки, не подменяйте
отсутствующие данные общей статистикой. Плановые остановки для копии также
оставляют разрыв в наблюдениях, а не успешные проверки.

По окончании первых семи суток приложение, наблюдение и ежедневные копии
продолжают работать без ограничения даты. Недельный итог сохраняется один
раз и не переписывается последующими наблюдениями. Прежние архивы автоматически
не удаляются. Защита свободного места остаётся: при нехватке новая копия
не создаётся, приложение не останавливается, ошибка записывается. Ошибка
подготовки числовой сводки не блокирует создание и проверку полной копии;
она отмечается отдельно в `reportStatus` и журнале службы.
Таймер не отправляет сообщений и не выключает сервер.

## Рабочие сайты

Добавляйте только адреса сервисов, которые вы имеете право проверять. Для HTTPS
оставьте проверку сертификата включённой. Например, можно проверить главную
страницу `https://shop.example.com/` и отдельный адрес готовности
`https://shop.example.com/health`. Учебные проверки `Pilot/*` держите отдельно.

Суточные числовые файлы пилота относятся к трём учебным проверкам. Для рабочих
сервисов используйте общую базу, копии и отчёты по выбранной группе. Для
обнаружения отказа самого сервера Kuma нужен внешний наблюдатель.

## Установка

Нужны Linux/amd64, Docker Compose с поддержкой `--wait`, Python 3.12+
и минимум 4 ГиБ свободного места. Для зоны `Europe/Moscow` нужна база
часовых поясов системы. Команды выполняются владельцем отдельной установки
через проверенный SSH. Это не универсальный установщик для чужих данных.

1. Собрать и проверить образ этой версии, перенести его на сервер,
   сверить SHA-256 архива и неизменяемый идентификатор образа.
2. Скопировать `compose.yaml`, `pilot.py` и файлы службы/таймера в новый
   отдельный каталог. Создать закрытый `pilot.json` с полями `project`,
   `image`, `imageID`, `port: 3041`, `days: 7`. Имя образа имеет вид
   `ub3dqy/uptime-kuma:pilot-<hex>`. Не использовать подвижную метку `latest`.
3. Выполнить `python3 pilot.py init`, затем `python3 pilot.py start`.
   Первая команда откажется принимать существующие данные или чужой проект.
4. Создать владельца через закрытый SSH-туннель, оставить вход обязательным,
   добавить только учебные проверки и группу. Записать в закрытый
   `data/pilot-monitors.json` числовые `userID` и `monitorIDs`. Файл должен
   принадлежать пользователю приложения 1000:1000 и иметь права 0600.
5. Подключить только нужный домен. Сначала использовать HTTP-шаблон:
   выдача сертификата разрешена, приложение закрыто ответом 503. После
   создания владельца получить сертификат и установить HTTPS-шаблон.
   Каждый раз проверять `nginx -t`, затем делать `reload`. Не перезапускать
   общие службы и не заменять конфигурацию чужих сайтов. В приложении
   включить доверие к прокси; шаблон перезаписывает входящие адресные заголовки.
6. Снять исходную полную копию, проверить архив и запуск отдельной
   восстановленной копии с выключенными проверками, без сети и внешних портов.
7. Выполнить `python3 pilot.py arm`. Установить два файла `uptime-kuma-pilot-watch.*`
   в `/etc/systemd/system/`, проверить их через `systemd-analyze verify`,
   выполнить `systemctl daemon-reload`, затем
   `systemctl enable --now uptime-kuma-pilot-watch.timer` и
   `systemctl start uptime-kuma-pilot-watch.service`.

У приложения нет прав администратора внутри контейнера, корневая файловая
система доступна только для чтения, память/нагрузка/размер журналов ограничены.
Данные и архивы находятся отдельно. Контроллер проверяет сервер Docker,
каталог, образ, метки и подключение данных перед операциями. Он не обновляет
образы автоматически и не удаляет прежние копии.

## Проверка и копии

В отдельном каталоге установки:

```sh
python3 pilot.py sample
systemctl status uptime-kuma-pilot-watch.timer
systemctl show uptime-kuma-pilot-watch.service -p Result -p ExecMainStatus
journalctl -u uptime-kuma-pilot-watch.service --since today
python3 pilot.py backup
python3 pilot.py verify-backup /srv/uptime-kuma-pilot/backups/<имя>.tar.gz
```

`sample` возвращает ошибку при нездоровом состоянии. Не считайте отсутствие
записи успешной проверкой. При сбое ежедневной операции повторной остановки
каждые пять минут не будет: сохраняется не более одной попытки в сутки.
После исправления можно вручную снять и проверить новую копию. Невыгруженная
часть периода сохраняется для следующей попытки; уже сохранённая сводка
не теряется при последующем сбое архивирования.

Копия включает весь каталог данных: базу, её настройки и вложенные файлы.
Для согласованности ненадолго останавливается только собственное приложение,
затем запускается и проверяется. Канал наблюдения этого интервала прерывается.
В описании архива есть начало, окончание сохранения и время повторного
готового запуска. Если места недостаточно, приложение не останавливается.
Архив и его описание с SHA-256 нужно хранить вместе. Копия на том же диске
не защищает от потери сервера: исходная проверенная копия также сохранена
в закрытой папке проекта на компьютере владельца. Дальнейшую внешнюю
ротацию следует определить перед постоянным рабочим использованием.

`verify-backup` извлекает только собственный архив в новый временный каталог,
проверяет состав и целостность базы, затем убирает эту временную копию.
Живые данные не перезаписываются. Для полноценного восстановления сначала
проверяют отдельную копию с тем же образом, без сети и активных проверок;
только затем планируют отдельное переключение с сохранением текущих данных.
Не извлекайте архив поверх работающей базы.

Пароль владельца, база и архивы закрытые. Их нельзя публиковать в Git,
отчётах или общих журналах. В приложении можно настроить второй фактор входа.
Для сертификата настроено автоматическое продление с проверкой и перечитыванием
nginx только после успешного обновления сертификата этого домена.

## Пауза и откат

Чтобы прекратить наблюдение, отключить только собственный таймер:

```sh
systemctl disable --now uptime-kuma-pilot-watch.timer
```

При необходимости остановить только своё приложение, предварительно
проверив `installation.json`, `pilot.json` и контейнеры:

```sh
KUMA_IMAGE='<образ из pilot.json>' KUMA_PORT=3041 docker compose -p uptime-kuma-pilot stop kuma
```

Данные, архивы и результаты сохраняются. Для отката домена используйте свою
копию прежней записи DNS и прежнего файла nginx. Сверьте, что оба относятся к
этой установке. Текущие тома Docker сохраняются.
