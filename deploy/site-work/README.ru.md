# Достоверный статус работ на сайте

Настройки источников для нескольких сайтов и объявления ручных работ хранятся
локально. Начните с примера `poll-many.example.json`.

Одна ошибка 503 не доказывает обновление. В примере источник
читает существующий, принадлежащий root признак
`/opt/example-service/shared/maintenance/enabled`. Файлы и процессы выпуска
остаются под управлением владельца сервиса. Наблюдатель их не изменяет,
не останавливает сайт и не запускает команды исправления.

Отдельная учётная запись `kuma-site-peer` по выделенному ключу может прочитать
только подготовленный небольшой файл состояния. Вход разрешён только с
основного узла, произвольные команды, переадресации, терминал и пароли запрещены. Ключ
владельца и ключи каналов ИИ/Telegram для этого не используются.

Основной узел проверяет точный адрес сайта, владельца и номер проверки.
Сигнал действителен 45 секунд; срок работ — 30 минут от времени исходного
признака, повторное чтение его не продлевает. После потери сигнала или
превышения срока обычные проверки возобновляются. Работы на другом сайте
не переводят эту проверку в обслуживание.

Во время подтверждённых работ сохраняются наблюдения «Обслуживание»:
доступность сайта не утверждается, время не превращается в успешные проверки.
В истории остаётся этап работ, сводки отдельно учитывают обслуживание.
Автоматический разбор ИИ и применение исправлений в это время блокируются.
После работ результат определяется настоящей проверкой сайта. Ошибка,
ожидание повторной проверки и потеря сигнала имеют разные тексты оповещений.
Старые сбои и доставленные сообщения задним числом не переписываются.

Файлы `*.service`, `*.timer`, `sshd-peer.conf`, `source.py`, `poll.py`
устанавливаются администратором с проверкой контрольных сумм и сохранением
прежних настроек. Конфигурация основного узла (`config.json`, права 0600,
владелец root) содержит только адрес узла, пути отдельного ключа/закреплённого
ключа сервера, `user=kuma-site-peer`, `monitorID`, `ownerID`, `siteHost`,
`output=/srv/uptime-kuma-pilot/data/site-work.json`.
Файл результата принадлежит пользователю приложения (1000:1000), права 0600.
Оба таймера работают раз в 10 секунд и не открывают сетевых портов.
Пауза до подтверждения сбоя должна превышать 20 секунд, чтобы успеть получить
сигнал работ. У подключённой проверки два повтора с промежутком 30 секунд;
её параметры подтверждаются перед установкой наблюдателя.

Для других проектов нужен столь же явный источник. Ошибки, содержимое
HTTP-страницы и догадка ИИ сами по себе не могут включить обслуживание.
Поддерживаемые причины: обновление, резервное копирование, плановые работы,
возврат версии. Обновление подтверждается записью незавершённого выпуска;
один общий признак обслуживания без такой записи означает только плановые работы.

Чтобы отключить интеграцию, остановить только собственные таймеры
`uptime-kuma-site-watch.timer` и `uptime-kuma-site-state.timer`.
Устаревший сигнал перестанет действовать через 45 секунд. Копии настроек
и история сохраняются без ограничения срока.
